The front door for every service.

Keep each app independent. Register its receiver once. Give clients one stable gateway URL and one revocable API key.

The flowRegisterReceiverClientAPI

How the link works

MeteorBase does not own your product data. It is the trusted middle layer: a client sends a request to the gateway, the gateway authenticates the client key, resolves the service slug, and forwards the request to your service receiver with private trust headers.

The public contract is always https://tinyapi-urjr.onrender.com/api/v1/<service>/<path>. Your service's real URL remains private in the registry.
01

Use X-API-Key: mb_live_…. The gateway checks the hash, expiry, revocation state, and service scope.

02

MeteorBase routes

The gateway checks the service registry and endpoint allowlist, then forwards the body, query string, and safe headers.

03

Receiver verifies

Your microservice verifies X-Internal-Secret and X-Service-Secret before running its normal route handler.

1. Register your microservice

Sign in as an admin, open the console, and create a service. Choose a lowercase slug, set the receiver URL, and optionally add endpoint metadata. The service secret is returned once. Put it in your microservice's environment variables.

POST /api/v1/admin/services Authorization: Bearer <your-supabase-access-token> Content-Type: application/json { "name": "oblivion", "display_name": "Oblivion", "webhook_url": "https://oblivion.onrender.com/meteorbase", "endpoints": [ { "method": "GET", "path": "/sessions" }, { "method": "POST", "path": "/sessions" } ] }

If you add endpoint rows, only the declared method and path pairs can be proxied. If no endpoint rows exist yet, the service stays in bootstrap mode and accepts any path after the key and service checks pass.

2. Install the receiver guard

Copy the reference helper from examples/meteorbase_receiver.py into the child app, or use the same logic in your framework. The receiver should share the gateway's INTERNAL_SECRET and its own generated service secret.

from meteorbase_receiver import require_meteorbase @app.get("/sessions") @require_meteorbase def sessions(): user_id = request.headers["X-User-ID"] return jsonify({"user_id": user_id, "sessions": []})

The service can expose any local route. It does not need to know the client API key; MeteorBase has already verified it. It only needs to trust the two server-to-server headers and use X-User-ID for user-scoped data.

Heartbeat

POST https://tinyapi-urjr.onrender.com/api/v1/apps/oblivion/heartbeat X-Service-Secret: <service-secret> Content-Type: application/json { "status": "ok", "latency_ms": 38 }

3. Call any connected service

Client applications use the same base URL regardless of which microservice they call. Generate keys from the console, store them in a server-side secret manager, and never expose them to public browser code.

const response = await fetch( "https://tinyapi-urjr.onrender.com/api/v1/oblivion/sessions", { headers: { "X-API-Key": process.env.MB_API_KEY, "Accept": "application/json" } } ); const data = await response.json();

Python clients can use the helper in examples/meteorbase_client.py, which maps to the same route contract for GET, POST, PUT, PATCH, and DELETE calls.
